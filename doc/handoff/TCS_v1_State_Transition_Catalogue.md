# TCS v1 State / Transition Catalogue

TCS Prototype v1 production handoff. Requirements describe the approved build contract, not infrastructure already delivered.

State axes are deliberately separate: account, verification, membership, financial fulfillment, timing, settlement and review status must not collapse into one status enum. Arrows summarize the implemented guarded operations, not arbitrary status-setting APIs. Prototype-only suffixes such as received-demo/approved-demo are fixtures, not production outcomes.

| Domain | States / valid progression | Actor / event | Guards | Audit |
| --- | --- | --- | --- | --- |
| KYC | required → pending; pending → verified/rejected/information-required; information-required → pending on response | Member submission/response; authorized verification reviewer | Complete contact/profile/evidence; immutable submitted snapshot; exact clients.verification.* action | Record submission, responses and reviewed decision |
| Organization application | draft → submitted → pending; review → approved/declined/information-required; response returns to review | Eligible Member/Owner; application reviewer | One owned Organization; required declaration; current review source | Submission snapshot and actor/reason; approval not activation |
| Organization workspace | approved → active after setup; restriction/suspension and permitted release; active → closure-pending → closed when cleared | Owner setup/request; permitted Internal review | Validated settlement and profile; closure obligations/cases clear; essential existing activity preserved | Activation, restriction source, clearance and decision |
| Join / participant | pending → approved/rejected; draft additions/removals; accepted terms recorded separately | Owner recruitment; Member commitment | Eligibility, draft capacity, source ownership; no deletion after financial commencement | Request source, decision and terms revision |
| Commitment / Position | Proposed assignment → accepted current revision; material edit invalidates acceptance; final order before activation | Owner allocates; Member explicitly accepts | Full/half only, capacity/max holdings and finalized order; no silence acceptance | Who accepted exact terms/order and when |
| Group / Cycle | draft → activated; draft or uncommenced activated → cancelled; activated → completed/completed-with-recovery or force-closed; new rollover/fresh draft after completion | Owner with readiness or controlled lifecycle action | Cancellation denied after any financial commencement; completion guards; Force Close approval; prior Cycle retained | Activation snapshot, financial boundary and reason; Group termination separate |
| Round | Upcoming → Open → Due → Grace → Late as clock progresses; resolution tracked independently | Effective schedule evaluation / process | Original due/open/grace dates; no invented obligation before opening; later Round does not erase earlier unresolved Round | Generated Round identity and actual/effective time |
| Obligation | Unpaid → Partially satisfied → Satisfied; optional not required or optional contribution made; timing independent | Trusted allocation and explicit Recovery recognition | Required and optional components separate; bounded allocation; no skipped-optional debt | Source transaction/allocation, principal component and date |
| Payment attempt | created/awaiting-payment → provider-pending/confirmed/failed/expired; retry creates another attempt | Member initialization; trusted provider event | Correct tenant/member/currency/reference/amount; failed attempt is not received money | Attempt lineage and provider success/arrival timestamps |
| Transaction / advance | confirmed unallocated → allocated/partially-allocated/exception; advance held until opening → eligible allocation | Provider confirmation and Round opening | Deduplicate provider reference; mismatch retains actual amount; reservation release once | Immutable received fact; allocation and hold/release link |
| Settlement | Expectation pending/delayed → partial/settled/exception as facts match; record unmatched/partially-matched/matched/variance | Provider reconciliation; permitted correction | Do not change payment timeliness or Member principal due because settlement lags | Original gross/fees/net, match links, correction reasons |
| Payout | ready → instruction-prepared → awaiting-confirmation or partially-paid; response → completed-member-confirmed/disputed; timeout → completed-window-elapsed; evidence decision → completed-operations-evidence/exception | Owner transfer; beneficiary; lifecycle process; authorized reviewer | Readiness, current bank snapshot, amount; partial plan; no Owner confirmation for beneficiary | Transfer and receipt distinct; preserve calculation, installments and evidence |
| Payout dispute | investigation → appeal-available → appeal-pending → final; final → exceptionally-reopened only by permitted intervention | Parties submit evidence/one appeal; independent reviewer decides | Configured evidence/appeal windows; original reviewer excluded; no bank-reversal invention | Keep original decision, appeal outcome, received amount and reopening reason |
| TCS share | due → overdue → restricted by configured windows; transfer awaiting-confirmation → confirmed and receivable settled; mismatch → exception | Owner records transfer; revenue_share.confirm Internal actor | Exact amount/account snapshot; no Owner self-confirmation; fees not netted off due | Receivable posting, transfer, independent confirmation and any later adjustment |
| Penalty | Eligible component/day → ACCRUED; partial/full waiver adds reduction; principal payment reduces future bases; end/clearance stops growth | Domain process; permitted Owner waiver | 0–10 bps accepted rate; grace expired; no compounding/optional charges; no rewriting posted day | Component/day uniqueness; principal basis, rate, business and actual time |
| Post-Payout Default | Eligible overdue required principal → retained POST_PAYOUT_DEFAULT event and linked Recovery | Domain evaluation after seven full local calendar days from grace expiry | Recognized payout receipt; excludes penalty-only/optional debt and unconfirmed transfers; zero penalty rate does not disable threshold | Default event never deleted by clearance; disjoint case scopes |
| Recovery | open → awaiting-review on clearance → resolved after review; restriction release only when applicable clearance holds | Recognized receipt; Owner review or authorized independent case action | Principal-first oldest-due then penalties; excess exception; dated receipt cannot pay future debt | Receipt/allocation scope, waiver, reviewer and retained default |
| Early Exit / settlement | requested → approved/declined; approved settlement due → resolved; overdue settlement may become Organization case | Member request; permitted Owner/reviewer; evidenced settlement | Before payout receipt only; preserve contributions; Owner beneficial exception needs independent review | Exit terms, recognition, due date, settlement confirmation |
| Replacement | proposed → awaiting-regularization → effective | Owner proposes; incoming Member accepts; recognized regularization | No replacement after payout; accepted terms and required prior value satisfied | Outgoing/incoming identities, Positions and effective handover |
| Amendment | awaiting-consent/pending-tcs-review → approved-awaiting-consent or approved-awaiting-application → effective; review may reject/request information | Owner proposal; affected Members; authorized TCS review | All required consent and oversight before apply; normal commercial changes next Cycle | Old/proposed terms, consent facts and approval |
| Force Close / termination | pending-tcs-review → approved/rejected/information-required; approved Force Close changes Cycle; separate termination closes Group | Owner initiation; specific Internal approval | Retain unpaid principal/penalty/payout/exit liabilities; no false payment or automatic Group termination | Balance snapshot, evidence, requested absorption, approving actor |
| Operations case | New → Assigned; In Review/Awaiting Information/Awaiting External Action/Awaiting Approval/Escalated through triage; Resolved/Closed follow governed source outcome | Authorized triage and source decision | Case status alone cannot mutate financial source; stale source preview rejected | Notes/assignment distinct from source decision audit |
| Internal user / role / session | Pending → Active; Active → Suspended/Deactivated; permitted activation restores eligibility; role active/inactive; session Active → Expired/Revoked; lock/unlock separate | Exact Access/Security actions | Current active unlocked authority; no self-escalation; protect last effective Access Administrator | Before/after, reason, historical authority, session/audit correlation |
| Business Date / runtime | REAL_TIME ↔ CONTROLLED in non-production; explicit target change; verification mode EMAIL/PHONE/BOTH | Authorized preview/apply | Current revision and actor; protected history; production rejects controlled date | Actual timestamp and before/after effective settings; no implicit process execution |
| Process run | RUNNING → COMPLETED/COMPLETED_WITH_NO_CHANGES/PARTIAL_FAILURE/FAILED; retry creates new linked run | Explicit run authority; retry authority distinct | Fresh preview, eligible environment-clock worlds, no concurrent execution; idempotent source writes | Immutable step results, counts, errors and retryOf lineage |

Source authority: each domain model and service under src/clients, organizations, groups, rounds, payments, payouts, lifecycle, penalties and reconciliation; src/operations/decisions.ts and interventions.ts; src/access/service.ts and security.ts; src/settings/service.ts; src/processes/service.ts. Rejected actions leave source history intact. Undefined transitions must not be inferred from a status label.
